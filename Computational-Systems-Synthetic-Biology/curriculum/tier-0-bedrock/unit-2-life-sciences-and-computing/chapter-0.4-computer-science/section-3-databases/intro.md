# Section 3: Databases

The first complete sequence of the human genome was announced in 2001. By the time you read this, the cost of sequencing an entire human genome has fallen below $1,000. In 2024, the gnomAD database contains whole-genome sequences from over 76,000 individuals. The Protein Data Bank holds over 215,000 experimentally determined structures. UniProt contains entries for over 250 million proteins. The AlphaFold database has predicted structures for essentially all of them.

Biology generates data at a scale that requires systematic storage and retrieval infrastructure. The question is not whether to use databases — it is which databases to use, for what purpose, and how to query them efficiently. This section covers three layers of the database landscape that every computational biologist encounters.

**Relational databases and SQL** provide the universal language for structured data. The metadata layer of any serious analysis — sample annotations, experimental conditions, QC metrics, analysis results — lives naturally in tables. More importantly, the major biological databases (Ensembl, UCSC Genome Browser, PharmGKB, DrugBank) are relational at their core, and querying them directly via SQL is far more powerful than using limited web interfaces. The subsection covers the relational model, normalization, core SQL operations (SELECT, WHERE, JOIN), subqueries, CTEs, window functions, indexing, and SQLite for lightweight analysis databases.

**Biological databases** are the substrate of all bioinformatics. Before any algorithm runs, you query at least one database: GenBank or RefSeq for sequences, UniProt for protein annotations, Ensembl via BioMart for gene coordinates, the PDB or AlphaFold database for structure, the Gene Ontology for functional annotation, KEGG for metabolic pathways, gnomAD or ClinVar for variant frequencies and clinical interpretations. The subsection covers what each database contains, when to use it, and how to query it programmatically via REST APIs and language-specific clients.

**NoSQL and big data storage** become necessary when the relational model breaks down — when data is too large for RAM, too heterogeneous for a fixed schema, or too high-dimensional for tables. Single-cell RNA-seq matrices with hundreds of thousands of cells, genomic coverage tracks over 3 billion positions, protein annotation records with wildly varying numbers of GO terms and literature references — each of these calls for a different storage strategy. The subsection covers key-value stores (Redis) for caching, document stores (MongoDB) for flexible schemas, HDF5 and Zarr for large numerical arrays, and the AnnData format that has become standard for single-cell genomics.
