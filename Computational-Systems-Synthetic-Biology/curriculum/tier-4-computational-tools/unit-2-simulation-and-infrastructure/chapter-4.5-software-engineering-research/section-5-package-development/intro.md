In the second year of a computational biology PhD, a student typically has a collection of analysis scripts that work. The scripts normalize RNA-seq data, build gene networks, run clustering algorithms, generate figures. Each script was written for a specific purpose, and each works for that purpose. Then comes the moment when a new experiment produces data that needs the same normalization logic — but the sample identifiers are in a different column, and the normalization function assumes a specific column ordering. The student copies the script, modifies it, and now has two versions. A year later there are six versions, each slightly different, none of which are documented, and nobody is sure which is correct.

This pattern — the script graveyard — is endemic to computational research. It arises from a completely understandable cause: exploratory analysis code is written for immediate purposes, not for reuse. The cure is equally understandable in principle but requires a deliberate structural investment: writing code as a package rather than as a collection of scripts.

This section covers the three components of modern Python package development for research code. The first subsection introduces the `src` layout — the directory structure that organizes package code, tests, and project metadata cleanly — and shows how well-designed modules with documented interfaces transform ad-hoc scripts into a reusable library. The `preprocessing.py` module developed here is a worked example: functions with clear signatures, type annotations, NumPy-style docstrings, and consistent handling of both array and DataFrame inputs. This is not more work than writing a script — it is the same work done in a way that compounds over time rather than accumulating debt.

The second subsection covers `pyproject.toml`, the modern standard for Python package configuration. Before this standard existed, a Python package required five or more separate configuration files. Now a single `pyproject.toml` declares build system, project metadata, dependencies, optional dependency groups, command-line entry points, and tool configuration for pytest, ruff, and mypy. The optional dependency groups are particularly valuable for research packages: users who only need the core analysis functions install a lightweight package, while developers and contributors get the full testing and linting stack with `pip install "bioanalysis[dev]"`.

The third subsection covers testing with pytest. The argument for testing research code is not that it's good practice in the abstract — it's that numerical bugs in analysis pipelines are the most insidious class of error in science. They don't produce error messages. They don't cause crashes. They produce subtly wrong answers that can be published, cited, and built upon before anyone notices. A test suite with fixtures, parametrized tests, and numerical tolerance assertions is the only systematic defense against them.
