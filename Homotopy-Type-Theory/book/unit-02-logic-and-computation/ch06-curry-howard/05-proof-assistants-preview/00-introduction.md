The dream of a machine that checks mathematical proofs is older than computers. What made it realizable is Curry-Howard: a type checker *is* a proof checker. If a proof is a term and a proposition is its type, then verifying a proof is exactly the same computational problem as verifying a typing derivation. Type checking is decidable — for well-designed type theories — and it can be done in time polynomial in the size of the proof term. The machinery for formalizing mathematics already exists in every compiler's type system; proof assistants are that machinery taken seriously.

What is surprising in the history is how early this became concrete. De Bruijn's Automath, from 1967, was formalizing portions of real analysis before most computers could fit in a single room. The current major systems — Lean 4, Coq (now Rocq), Agda, Isabelle — are not recent discoveries but the mature state of a sixty-year development. Each embodies a different point in the design space: Coq's calculus of inductive constructions emphasizes tactic-based proof with a small trusted kernel; Agda's design is closer to MLTT with first-class pattern matching; Lean 4 targets industrial-scale mathematical formalization with a focus on automation.

This section is a preview, not a tutorial. Its purpose is to make the connection between the type theory you have been studying and the systems you will eventually use concrete enough to be motivating. When you write `theorem`, `def`, and `fun` in Lean, you are writing terms in a dependent type theory. When the elaborator accepts your proof, it has run the type checker against the proposition. Nothing more is required. The gap between the formal systems in this book and the tools of contemporary automated reasoning is smaller than it appears — the main bridge crossed is the one built by Curry-Howard.
