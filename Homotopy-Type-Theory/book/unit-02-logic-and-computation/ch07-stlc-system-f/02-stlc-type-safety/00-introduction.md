Type safety is the formal statement of the promise that types make: a well-typed program never goes wrong. "Going wrong" has a precise meaning here — a *stuck state*, a configuration where evaluation should continue but no rule applies. The untyped term $3 + \mathsf{true}$ gets stuck because addition has no rule for boolean arguments. The typed version of this term cannot be formed: the typing rules would reject it before evaluation begins. Safety is the theorem that the type rules exclude exactly the terms that would get stuck, and nothing more.

The proof splits into two lemmas with a memorable name: *progress and preservation*. Progress says a closed, well-typed term either is already a value or can take a step — it is never stuck. Preservation says that if a term has type $A$ and takes a step, the result also has type $A$ — typing is stable under reduction. Together they give a clean induction: start with a well-typed term, apply progress to get a step (or a value), apply preservation to maintain the type, and repeat. The computation never halts unexpectedly and the type never changes.

Progress and preservation are the canonical form of type safety arguments across all of type theory. When a new type construct is added — dependent pairs, identity types, higher inductive types — the proof that the extended system is well-behaved is always a version of this argument. You will encounter it again in every extension, and the habit of checking both properties together becomes a reliable diagnostic: if a proposed type rule breaks either lemma, the rule is wrong. Learning the argument here, in the STLC setting where every case is elementary, gives you the template for every subsequent safety proof.
