System F allows terms to quantify over types. System F$\omega$ takes the next step: it allows *types* to be defined by functions from types to types, and it provides a type-level lambda calculus to write those functions. A type like $\mathsf{Maybe}$ — which takes a type and returns a type — has kind $\star \to \star$, and in F$\omega$ you can write it as a type-level lambda abstraction $\lambda \alpha : \star.\, \mathbf{1} + \alpha$. Kinds classify types the way types classify terms, and the full grammar of kinds is a copy of the grammar of simple types.

The resulting system sits at a precise position in the lambda cube — Barendregt's classification of typed lambda calculi by three binary dimensions: types depending on types (F$\omega$), types depending on terms (dependent types), and terms depending on types (System F). F$\omega$ adds the first dimension to STLC; dependent type theory adds the second; the calculus of constructions adds all three. F$\omega$ is therefore not just an endpoint but a position in a space, and understanding it makes the geometry of that space legible.

F$\omega$ is also where Haskell's type system lives: type classes, functors, monads, and the entire apparatus of Haskell's higher-kinded abstraction are fragments of F$\omega$. The kind system of Haskell — `* -> *` for `Maybe`, `(* -> *) -> Constraint` for `Monad` — is a syntactic restriction of F$\omega$'s kind grammar. Studying F$\omega$ formally is therefore not an academic exercise for the programming language practitioner; it is understanding the foundations of the language you may already be using. And for the HoTT researcher, it is the last station before dependent types, where types depending on terms collapse the boundary between the type and term languages entirely.
