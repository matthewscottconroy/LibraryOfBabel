Ordinary pairs are incurious about their own contents. A pair of type A × B holds an A and a B, and the B has no knowledge of which A it lives alongside. Σ types change this: the type of the second component is allowed to depend on the value of the first. A Σ type Σ(x:A).B(x) contains a specific element a : A and an element of B(a) — the type family B applied to that particular a. The two components are linked at the level of types, not just values.

The canonical example makes the idea concrete: the type Σ(n:ℕ).IsEven(n) pairs a natural number with a proof that it is even. You cannot swap the number for a different one and keep the proof, because the proof's type refers to the specific number. The Σ type enforces this coupling automatically. What is surprising is how much this simple coupling expresses: existence with a witness. The existential quantifier ∃x.P(x), in dependent type theory, is exactly Σ(x:A).P(x). A proof that some x satisfying P exists is a pair — the witness and the proof — and both are first-class computational objects you can extract and use.

This is the point where logic and computation begin to fully merge. In classical mathematics, an existence proof gives you a guarantee without necessarily giving you the object. In dependent type theory, Σ types ensure that existence proofs are always constructive: the witness is inside the proof, extractable by the first projection. This computational content is what makes automated theorem provers useful for extraction — a proof of Σ(l:List).IsSorted(l) does not just certify that a sorted list exists; it hands you the list. The same structural move that gives you dependent pairs gives you the existential quantifier, and the same structure that gives you the existential quantifier gives you the total space of a type family — a concept that becomes central in HoTT.
