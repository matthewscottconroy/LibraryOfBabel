Every proof assistant commits to a primitive, and Lean 4's primitive is the *type*. Not the proposition, not the set, not the formula in a logical calculus — the type. Every object you will encounter in Lean 4, from natural numbers to group homomorphisms to the proof that a homomorphism's image is a subgroup, is a term with a type, and that type determines everything the system can verify about it. This is not an implementation detail. It is the Curry-Howard isomorphism made load-bearing: propositions are types, proofs are terms, and the type checker is the proof verifier.

This section grounds you in the mechanics before the mathematics. You will install Lean 4 via `elan`, create a project wired to Mathlib, and learn to read the infoview — the interactive display of what the system currently knows and what it still needs from you. The infrastructure matters: Lean's build system `lake` and the precompiled cache for Mathlib are not incidental logistics, they are what make working at scale tractable. Getting the environment right is the precondition for everything that follows.

What you are learning here is a new discipline of notation. The term-level syntax of Lean 4 — `fun`, `match`, `→`, `×`, `∃` — will look familiar if you have written typed functional code before, and alien if you have not. Either way, you are learning to think about mathematical objects in a form that a machine can check. The gap between informal mathematics and formal Lean 4 is real, and this section is where you begin to close it.
